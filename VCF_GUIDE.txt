Keep multiple phone numbers when importing a vCard into a workflow

Problem: mapping only the first phone or email can discard useful contact data.
Our VCF Actor returns arrays and retains original fields and warnings.

Downloadable synthetic input: contact-import-sample.vcf in this repository.
Expected source values: two TEL fields, two EMAIL fields, and the grouped Desk
label. The phones and addresses are invented examples, not customer data.
Opening the file starts no hosted run; a manual CRM import would change that
destination, so use only a test environment. Exporter/CRM compatibility and the
fixture's hosted execution have not been verified. Use the checklist below.

Use examples.py from this folder:

from pathlib import Path
from examples import call_actor, contact_rows
result = call_actor('vcard-to-json', 'vcard_text',
                    Path('contacts.vcf').read_text(encoding='utf-8'), '0.02')
rows = contact_rows(result)

Set APIFY_TOKEN via your secret manager/environment. Do not store it in code.
Review warnings before writing to your CRM. Each row keeps all phones/emails;
map arrays into a destination that supports multiple values, or retain them in
an associated table. original retains labels and source fields. Overwriting a
single CRM phone field repeatedly will still lose values at the destination.

started a paid run: inspect the existing run before retrying.


Before enabling CRM writes
1. Try a synthetic contact with two different phone numbers and two emails.
   Verify the destination still contains every value after mapping, not just
   that the Actor returned arrays. Keep source labels alongside each value.
2. Review parser warnings and keep the original export available for comparison.
   A parsed row is not proof that a number or address is current or belongs to
   the intended person.
3. Decide your matching policy before import. A source UID, when present, needs
   a source/address-book namespace; do not assume the same UID from different
   exports identifies the same person. Missing UIDs need an explicit policy.
   Shared family emails and switchboard numbers are unsafe automatic merge keys.
4. Preview proposed creates, updates and conflicts without writing. Route
   ambiguous matches for review rather than merging or deleting contacts.
5. Keep an import ledger keyed by source and your chosen stable identifier.
   On retry, reconcile already completed writes instead of creating all rows
   again. The Actor prepares contact data; it does not make CRM writes
   idempotent or roll them back.
6. Make replacement versus append behavior explicit. An absent input value
   should not silently erase a manually maintained destination field. Test the
   CRM's array and label behavior on synthetic contacts before bulk changes.

Acceptance checklist: two phones retained, two emails retained, labels reviewed,
ambiguous matches withheld, and replay of the same synthetic import produces
no duplicate contact. These are checks for YOUR integration, not claims that
this repository has tested a CRM or provides an automatic matching engine.
