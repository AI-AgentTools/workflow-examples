Prepare long Markdown reports for Telegram without parse_mode

Problem: long reports and formatting boundaries need preparation before sending.
The Actor returns ordered text and Telegram entities. It does not send messages.

Use examples.py from this folder:

from pathlib import Path
from examples import call_actor, telegram_payloads
result = call_actor('telegram-message-preparer', 'markdown',
                    Path('answer.md').read_text(encoding='utf-8'), '0.01')
payloads = telegram_payloads(result)

Set APIFY_TOKEN in your secret manager/environment. Review the result and send
payloads sequentially with your own sender. Add chat_id and preserve entities.
Do not also set parse_mode. Keep the bot token in your sender, not Actor input.
Respect rate-limit responses and record successful deliveries. A timeout is
ambiguous; blindly retrying a message or Actor call can duplicate work.

For n8n, import n8n-telegram.json. Select an Apify Header Auth credential with
Authorization: Bearer followed by your own token. Replace synthetic input with
your upstream text. The workflow emits ordered prepared items for your sender.

Keep text and entity offsets together
Telegram entity offsets and lengths use UTF-16 code units, not Python character
indexes or UTF-8 byte counts. For text "😀 bold", the word "bold" starts at
UTF-16 offset 3 and has length 4: the emoji occupies two units, the space one.
An offset of 2 from Python's character index would select the wrong range.

Offline arithmetic check (no token, network or message):
   text = "😀 bold"
   prefix = text[:text.index("bold")]
   offset = len(prefix.encode("utf-16-le")) // 2
   length = len("bold".encode("utf-16-le")) // 2
   assert (offset, length) == (3, 4)

After preparation, do not prepend a heading, trim whitespace, normalize text,
replace characters or slice a message while reusing its original entities.
Such edits can invalidate offsets even if the message still looks similar.
Prefer applying your desired text changes BEFORE preparation. Your sender adds
chat_id separately and sends each returned text/entities pair unchanged, in
order, without parse_mode. If you must edit prepared text, regenerate and
validate its entities instead of adding a guessed offset to every entity.

This example checks indexing arithmetic only. It does not establish Telegram
rendering, supported formatting combinations or actual delivery. A downstream
sender remains responsible for credentials, rate limits and ambiguous retries.
